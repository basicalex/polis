Local-first civic infrastructure

Officials campaign and govern on the same verifiable rails that hold them accountable.

Polis is a monorepo of source-linked governance maps, hash-chained public audit trails, cryptographic proofs (RFC 3161 timestamps and CMS institutional e-seals), and proof-oriented transition pilots. Public reads need no authentication, no ranking, no persuasion primitives — only the same evidence anyone else can independently verify.

Proof is not truth. The system proves provenance and integrity — that a document existed at a time, was sealed by an institution, and has not changed since — never that its contents are correct. Judgment stays with the reader.

Section 1

Who Polis serves

Every surface is scoped to one of five concerned parties. The value proposition for each is defined by what they can verify, file, adjudicate, or seal — never by what the platform asserts about them.

Citizens

Read the record, verify it themselves, deliberate on it.

  • Browse governance-graph reads (jurisdictions, processes, claims, evidence) with no login.
  • Verify any file locally in the browser — SHA-256 hashing runs client-side; files never upload.
  • File questions on published commitments through the contribution service.
  • Read the hash-chained public audit trail with redactions applied.

Verified officials & mandate-holders

A drafting surface — never a self-endorsement surface.

  • File commitments (proposal-assertions or public statements) tied to an accepted charter.
  • File resolution claims when the commitment is answered by evidence.
  • Answer citizen questions in the open, on the record.
  • Cannot self-mark a commitment as delivered — only reviewer adjudication can.

Reviewers

The only path to a terminal commitment status.

  • Adjudicate submissions in the §19 review queue.
  • Approve or reject resolution claims; approval emits an append-only status event.
  • Bound by representative/status.rego — terminal transitions require an approved resolution.
  • Every decision is audited with correlation ids linking claim, evidence, and outcome.

Institutions & municipalities

Ingest, seal, and archive — with proof-oriented pilots.

  • Route documents through the ingestion gateway into Paperless-ngx (real mode) or the deterministic stub.
  • Apply CMS institutional e-seals via the signature service (eIDAS-style seams; test keys locally).
  • Anchor everything to RFC 3161 timestamps via the timestamp service.
  • Operate the citizen vault with policy-controlled document grants.

Independent verifiers & journalists

A standalone verifier app — no account, no upload.

  • Standalone Astro app at apps/verifier (port 4322) surfaces the eleven verdict states.
  • Verify by hash, by file (client-side hashed), or by proof id — proofs deep-link to the audit chain.
  • Issuer registry and revocation/supersession lookups make provenance auditable end-to-end.
  • Proof manifests are self-contained: RFC 3161 tokens embed the TSA cert chain.

Partner pilot organizations (M15)

The chartered pilot slot for a real jurisdiction.

  • Replaces the seeded simulated "Grad Primjer" jurisdiction with a real charter.
  • Gates on M10 (real OIDC identity) and M14 (real upstream Polis deliberation).
  • Charter fields are operator env — no code path or public schema changes required at the pilot boundary.
  • Composes with the M-RA loop for a real chartered mandate-holder.

Section 3

Trust machinery

Provenance and integrity are enforced by four mutually reinforcing mechanisms. None of them requires trusting Polis itself — every claim is externally checkable.

Hash-chained append-only audit

Every material event is written to the audit service with a hash and previousHash pointer (spec §26.3). No UPDATE, no DELETE. Public reads apply redactions server-side; the chain itself is inspectable end to end.

append-only redacted reads

Policy-as-code (OPA / Rego)

Access, AI safety, rewards, pilot governance, and the representative-accountability rules all live as Rego bundles in packages/policy-rules, each with real opa eval decision tests. Structural absence of persuasion computations is enforced by what the policy does not compute.

access.rego ai.rego rewards.rego pilot.rego representative/*.rego

Client-side file verification

The verifier app hashes uploaded files with SHA-256 in the browser and compares against the proof manifest. Files never leave the client. The privacy note on the drop zone reflects this in the design system (.privacy-note).

no upload SHA-256 in-browser

eIDAS-style seals and RFC 3161 timestamps

Proof manifests bind a document hash to a CMS institutional e-seal (the signature service) and an RFC 3161 timestamp token (the timestamp service). In real mode both flip to a qualified TSP / TSA behind the same factory; stub mode uses self-contained test material and is explicitly marked as such in the verdict.

CMS seal RFC 3161 test-signature note in stub

Eleven verification verdict states

Composed by composeVerificationVerdict in packages/domain/src/verdict.ts. Each verdict carries a tone that maps to the trust-badge palette shared by all four apps.

valid Hash, signature, timestamp match; issuer known; registry active.
valid_but_superseded Proof is intact but a newer supersession exists.
valid_but_expired Registry entry is past its expiry window.
revoked Issuer or registry has revoked the proof.
integrity_failure File hash does not match the manifest hash.
signature_invalid CMS e-seal verification failed.
timestamp_invalid RFC 3161 token verification failed.
issuer_unknown Issuer not present in the registry.
status_unknown Registry cannot confirm current status.
private_or_restricted Proof exists but is not publicly readable.
not_found No matching proof or hash lookup.

Section 4

The representative-accountability loop (M-RA)

Politicians gain standing only by filing checkable claims and surviving follow-through review. Nothing here computes rankings, grades, or win-probability — the platform is structurally incapable of endorsement.

Step 1

Charter accepted

A verified_official holds an active mandate_holders row with an accepted mandate_holder_charters row that covers the process and jurisdiction.

Step 2

Commitment filed

Official files a claim (proposal-assertion or public statement) plus a commitments row via contribution-service. Published to the public record.

Step 3

Citizens ask

Questions are filed as submissions against the commitment. Answers by the official are on the record and hash-chained.

Step 4

Resolution claim

Official files a resolution claim with evidence. The caller cannot self-assign delivered.

Step 5 · decision

Reviewer adjudicates

A reviewer approves or rejects. Only reviewer approval emits the append-only commitment_status_events row that sets a terminal status. overdue is system-derived — never set by a human.

Step 6

Scorecard deep-links

Counts by status, every number deep-linked to the underlying evidence and audit rows. No ranking. No grade. No comparison across officials.

Governance invariants

  • Follow-through is never self-reported — terminal status requires an approved resolution.
  • Status is append-only, latest-row-wins in commitment_status_events.
  • The scorecard is pure fact — counts by status, every number deep-linked to evidence.
  • Publication requires a verified, active mandate-holder with an accepted charter.
  • No persuasion primitive, ever — no targeting, messaging, GOTV, donor, or opponent tooling.

Evidence redaction

Commitment evidence that identifies constituents defaults to restricted and is redacted in public §26.4 reads. Reviewers see the un-redacted view under access-control policy; the public sees only what the audit chain permits.

Every public surface carries the [accountability, not endorsement] tag next to the existing [public-read] and [verifiable] tags.

Section 5

Adapter seams and production modes

Every external integration is behind an env-driven factory. Stub is the default and stays green. Flipping a *_MODE switches in the real adapter behind the same contract; unknown modes throw fail-fast, never silent fallback.

Concern Env Stub (default) Real mode
AI provider AI_MODE Deterministic RAG over approved public sources. External model provider behind createModelProvider().
Institutional signature SIGNATURE_MODE Test-key CMS seal; verdict flags "test signature". EU DSS / qualified TSP.
Timestamp authority TIMESTAMP_MODE Deterministic RFC 3161 stub token. Real RFC 3161 TSA endpoint (self-hosted sigstore or qualified TSA).
Upstream deliberation POLIS_MODE In-repo bridge stub for local demos. Real upstream Polis instance for deliberation.
Document repository PAPERLESS_MODE Deterministic paperless-adapter stub. Self-hosted Paperless-ngx over HTTP.
Identity provider IDENTITY_MODE HMAC sessions + magic-link dev tokens. OIDC (Keycloak in compose; production IdP via operator env).

The two seams that had to be introduced during productionization (M10 identity and M13 AI provider) each add the create*Client() abstraction as their first step, then wire the real adapter behind the same factory. Every other seam was ready at end of M9.
